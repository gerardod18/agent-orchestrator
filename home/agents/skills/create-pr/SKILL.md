# Create PR

Use the user's base branch, otherwise `main`. Separate preparation from publication. A request to prepare a PR authorizes a local draft only. A request to create/open a PR, and finished implementation work whose checks and reviews pass (shared policy, auto-publish), authorize the necessary branch push and PR creation, followed by scoped `pr-followup` remediation. Approval of the draft is not authorization to push. Use existing explicit authorization for each action; do not ask again for an action already authorized for the same scope and branch state.

In dev-team, only the Publisher executes this skill. The Lead supplies the user's request, action authorizations, branch/base/HEAD, check/review evidence, and skill bindings. Return drafts, blockers, and missing decisions to the Lead for user interaction. Never treat the Lead's delegation alone as user authorization. Resolve this skill and its dependencies in the current product's personal skill directory; if a required skill is missing, return its exact name.

## Prepare (read-only with respect to the repository)

1. Read root and nearest applicable `AGENTS.md`. If repository `.agents/skills/create-pr/SKILL.md` exists, treat it as input only (title format, body sections, checklist, required checks); this shared skill still owns the lifecycle through `pr-followup`, so the task does not end at PR creation. User limits still apply. Before external access, report actual access and missing requirements. Never request secrets in chat.
2. Inspect `git branch --show-current`, `git status --short`, `git log --oneline <base>..HEAD`, and `git diff --stat <base>...HEAD`. Resolve base and HEAD and tie the draft/evidence to them. Stop for uncommitted changes or no commits against the base; PR preparation never implicitly authorizes committing or staging.
3. Apply the `commit` skill's branch-and-ticket preflight: a local unpublished branch with a non-conventional or tool-generated name is renamed automatically to `<type>/<ticket-id>-<slug>`; a Linear ticket is created from the work when none exists. Never invent an ID.
4. Check lint, format, typecheck, tests, and required CI-equivalent evidence for this exact head/snapshot. Within dev-team require both canonical review reports too. Report missing/stale evidence and route it to the Lead for the Implementer/reviewers. Outside dev-team, run missing authorized local checks before publication. Never label incomplete validation as passed.
5. Prepare the complete title (Conventional Commit format, for a single commit identical to its subject; at most 72 characters) and body. Use the repository's template when one exists (`.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE/`, `docs/`). When none exists, use this built-in template: What changes, Why, How to test, Risks and rollback, Ticket (Linear link). Do not add a template file to the repository unless asked. Describe the final change and actual validation.
6. Return the complete draft plus the exact proposed actions and any blockers. An explicit request to create/open the PR authorizes drafting its title/body and publishing; do not add a separate draft-approval checkpoint. Ask only for an unresolved material decision or missing publication authorization. A prepare-only request ends here.

## Publish (only authorized actions)

1. Recheck branch, base, HEAD, clean working tree, and evidence. If they changed, update the draft and affected evidence; refresh draft text automatically within scope; obtain renewed authorization only for a material scope expansion or a newly unauthorized action. In dev-team, a changed snapshot requires revalidation and both reviews through the Lead before publication.
2. Confirm the user authorized PR creation. Confirm a direct push request or the shared policy's authorization for creating/following up this PR. Draft-text approval alone does not authorize a push. If the exact head is already on the intended remote branch, no push is needed. Inspect existing PRs for this head/base and return the matching PR instead of creating a duplicate; do not update an existing PR without applicable authorization.
3. Before an authorized push, read and apply `ci-prepush-guardian`, adapting commands/base to repository instructions and covering any additional required CI gates. A failed, stale, or incomplete required gate blocks the push. Within dev-team, source fixes, hook edits requiring repair, and conflicts go back through the Lead to the Implementer; the Publisher does not edit application code. Scoped correction pushes reuse recorded follow-up authorization. The guardian performs the push; this skill never pushes a head the guardian already pushed. Set upstream when needed with an explicit remote and branch.
4. Create the PR for the confirmed remote head using the approved base, title, and body. With `gh`, use `gh pr create --base <base> --head <branch> --title <title> --body-file <path>`. Store the exact body outside the repository under `~/claude-plans/<repo>/`, or send it through stdin with `--body-file -`. Use safe argument handling and preserve real newlines. Do not interpolate PR text into shell code. If the user explicitly authorizes a draft PR on an already-pushed head despite unavailable checks, use `--draft` and state the missing checks; it is not ready. Dev-team's validation gate still blocks publication when required evidence is incomplete.
5. In Codex, attach every created PR to the current chat with `attach_artifact` when that tool is available. Return the PR URL, branch/base/head, actual actions and check evidence. If creation returns an ambiguous result, inspect existing PRs before retrying.
6. After publication, continue `~/.agents/skills/pr-followup/SKILL.md`; in dev-team the parent dispatches this loop. Inspect every expected CI job and unresolved review thread for the current PR head. Pending, skipped, missing, or failed required jobs and unresolved threads prevent a ready verdict. Report infrastructure blockers; send code failures through the Lead for the Implementer. Do not merge or deploy.

If `gh` or authenticated access is unavailable, return the approved title/body and the exact blocker. Do not claim a PR was created. A UI fallback is available only with appropriate access and the same action authorization.
